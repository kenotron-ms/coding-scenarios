The work capsule

A definition of done a machine can prove — and a human can approve in minutes.

A work capsule is two files: DEFINITION.md, the human-approvable spec, and DEFINITION.verify.sh, an executable gate whose exit code is the definition of done. The trick is not the gate; it is what the pipeline proves about the gate before anyone is asked to trust it: that it goes RED on the unfixed code for the stated reason, that it is not vacuous, and that it is not so broad it passes on anything. Two Attractor graphs bracket the capsule — one builds and proves it, the other consumes it to write real code until it turns GREEN and two independent critics agree.

Built on: capsule.dot (specify — build & prove) · task-runner.dot (implement — build until green) · the Attractor engine (fail-closed goal_gates, convergence loops, must_write contracts)

01The problem

"Done" is a sentence nobody can run

Hand an LLM a task and it will tell you when it is finished. That is the whole problem. The definition of done lives in prose — in the issue, in the acceptance criteria, in the model's own summary of its own work — and prose is not executable. Nothing checks it. Nobody re-runs it.

Three failure modes follow, and they are not hypothetical:

  • The model grades its own homework. If the only thing between a run and "done" is the worker's assessment of its own output, a single plausible-but-wrong response ends the run successfully.
  • An unproven gate passes on anything. A test that never actually failed on the broken code proves nothing when it passes on the fixed code. It might pass on everything.
  • A gate can pass a lie. A check that greps for a success string, or pipes its own exit status away, will report success over a red test suite — and every CI light stays green, because nothing downstream executes it.

The work capsule's answer is to refuse to treat "done" as prose. It compiles the definition of done into a script, and then — before a human is ever asked to approve it, and before a single line of the real fix is written — it spends a whole pipeline proving that the script is a good judge. The proofs are the point. The capsule is what survives them.

"A capsule PR is a proposal that a human is asked to approve on the strength of proofs about a script; if the script that arrives is not the script that was proven, the proofs are worthless and nothing notices."

— verify_shipped_gate.sh, on why the shipped bytes are re-checked

02The big idea

A definition of done, compiled to a gate — and proven before it is trusted

The specify graph carries one sentence, and everything it does is in service of it. It is worth reading in full, because it is not a description of the capsule — it is the goal the graph converges on:

"Given an issue-shaped report and a pinned base SHA, produce a work capsule (DEFINITION.md + DEFINITION.verify.sh) that is machine-proven RED-for-the-right-reason at that SHA and non-vacuous, judged behavior-bound by one critic, and authored in upstream-legal vocabulary — a definition of done a human can approve in minutes."

— capsule.dot, the goal= attribute

Unpack that and every clause is a proof obligation:

  • a pinned base SHA — the gate is proven against one exact commit, written to .ai/base-sha and shipped as the capsule's base_sha. Every measurement in the pipeline first proves the tree actually sits at that SHA, because a dirty tree poisons every verdict downstream.
  • machine-proven RED-for-the-right-reason — run at that SHA the gate must exit 1 and emit a declared red_signal string, so the red is the bug rather than an unrelated crash.
  • non-vacuous — a crude, deliberately-wrong patch must be able to turn the gate green, proving the gate is reachable at all and not satisfied by nothing.
  • judged behavior-bound by one critic — machines settle the facts; a single independent judge (a second model family) rules on the residue they cannot decide, and its verdict is anchored to an exact line.
  • upstream-legal vocabulary — the DEFINITION is scanned for leaked internal terms before it can ship, so a public capsule PR reads clean.

The governing doctrine

The graph states its own philosophy in its header: "Machines prove facts. One judge rules the residue machines can't decide. Nothing with a measured miss record gets acquittal power over an executed result. Every gate is born advisory, names the goal clause it enforces, and carries a retirement condition." That is why the pipeline is mostly mechanical checks with exactly one LLM judgment node — and why lessons land as one-line charter rules, not as an ever-growing pile of nodes.

03What's novel

The proofs that make a gate trustworthy

Any project can write a test and call it a spec. What is distinctive here is the ring of adversarial proofs the pipeline runs against its own gate before shipping it — and the incidents, recorded in the graphs themselves, that each proof was bought with.

01

Red for the stated reason

A gate that fails on the broken code is necessary but not sufficient — it could be failing because the file does not import, or the interpreter crashed. The redgate node requires both conditions: the gate exits 1, and the DEFINITION's declared red_signal string appears in the run's log. Only then is the red "red for the stated reason rather than an unrelated crash."

"rc==1 AND the declared red_signal appears in the red run's log."

02

Non-vacuity, proven by two crude fixes

Before the gate is trusted, three adversarial patch-writers attack it. mutate writes a deliberately crude hypothesis patch — "that hardcodes, stubs, or early-returns its way to making the gate exit 0. This is explicitly NOT a correct fix." mutate_b writes a second one that must be "DIFFERENT IN SHAPE, IDENTICAL IN OBSERVABLE OUTCOME." If two mechanically-different hacks can both green the gate, the gate is reachable and not welded to one guessed fix. Both crude patches ship in the capsule folder as .hypothesis.patch and .hypothesis-b.patch, so the reviewer can see the escape hatches the gate deliberately allows.

03

The void ratchet — dodges that never come back to life

The third attacker, void, tries to defeat the gate by deleting the witness — disabling the very assertion that catches the bug. Any void patch that greens a gate draft is archived durably (content-deduped, capped at eight), and here is the ratchet: nonvacuity_gate re-runs every archived dodge against the current gate on every round, under a bounded time wall — never a silent skip. A hole you closed in round two cannot quietly reopen in round five.

Honest scope — the named residual

The ratchet's own comment refuses to overclaim: "this ratchet is ANTI-FORGETTING, not ANTI-ADVERSARY. The archive and the ledger are worker-writable… nothing here prevents that deletion; what it now does is make it VISIBLE." Every guard in the system names the attack it does not close and the condition under which it can retire. That honesty is a design rule, not a footnote.

04

Discrimination — the gate that isn't over-broad

A gate can be red-for-the-right-reason and still be too broad — red on the bug, but also red on unrelated code that has nothing to do with it. The discrimination_check exit gate runs the gate at an unrelated later commit and requires it to go red there too, catching "a gate that passes on anything." It is the one proof that is skippable — with a written reason — when no later commit is supplied.

Read this before you trust a capsule

Because this proof is skippable, a capsule can ship with its .discrimination.md recording DISCRIMINATION: skipped — no later_commit supplied — meaning the over-broadness check never ran. Take a capsule whose gate greens the fix and prints the right red_signal at its base SHA, but whose discrimination line reads skipped: the gate may still be sound, yet that one assurance is simply absent, and the capsule says so on its face. That is the discipline the record enforces — it tells you what the pipeline did not check, so you weigh the gap before trusting the gate.

05

One judge to specify, two who must agree to implement

Machines settle facts; judgment is where a model earns its keep — and the design rations it. In specify, a single critic from a second model family rules on the residue and its verdict is anchored to an exact line (^VERDICT: SHIP$ / ^VERDICT: ITERATE$) so it cannot be faked by chatty prose. In implement the bar is higher: two critics from different families review independently — "Do NOT read the other's file… independence is what makes agreement meaningful" — and the deterministic verdict ships only if both say SHIP. Disagreement is treated as signal, not noise.

"ok=1; [ "$a" = ship ] && [ "$b" = ship ] && ok=0"

06

A loud dead-end for corrupted state

Not every stop is a failure to converge. When a reset cannot be proven — the tree was supposed to return to base and the pipeline cannot show that it did — the run routes to reset_fail: a node with no outgoing edges at all, non-retryable, deliberately loud. "A reset that cannot be proven is a corrupted-state class." It is distinct from a budget-exhausted stop (which writes a postmortem) and from a reasoned human escalation. The system draws a hard line between "this failed to work," "this needs a human," and "the ground under this run is no longer trustworthy — halt now."

Three incidents, recorded in the graphs

These proofs read as paranoia until you see what they were bought with. The graphs carry their own scar tissue:

The gate nobody executed

A capsule PR shipped a verify.sh containing 54 [REDACTED:assignment] markers across 31 lines. The in-run judge approved a gate that ran; a secret-scrubber then rewrote the script before the branch was pushed. "Every CI check on that PR was green, because NOTHING anywhere executes a shipped capsule gate." The fix: a byte-for-byte record/verify fence, and a step that re-runs the shipped bytes from a clean tree — because the proofs are about the script, and the script that arrives must be the script that was proven.

Consensus that quietly became one voice

In a real run, the second critic hard-errored on all five attempts (no adapter found for provider 'openai') and burned the entire budget — despite a gate-green fix sitting right there. A two-family agreement mechanism is only as good as its second family actually being present; when it silently collapses to one, "consensus" is theatre.

The phantom SHIP — stale evidence

A prior round's critique file, read as if it were the current round's verdict, ships a fix the current round never actually judged. The engine's per-visit must_write freshness floor is what closes it: a node that promised an artifact this round and did not produce one cannot pass on last round's.

04Under the hood

Two graphs: one builds the capsule, one spends it

Both stages are Attractor pipelines — DOT graphs where nodes are computation, goal_gate edges are fail-closed, and every worker node that promises an artifact must actually write it. Read them for shape, not size: what matters is the order of the proofs, not the node count.

Specify — capsule.dot, the build-and-prove graph

A read-only pipeline: it produces a proven capsule and copies it out, without committing anything. The spine runs authoring first, then a wall of proofs, then a single judgment, then the exit gates.

The preflight that fails loud

The very first node, setup, is deterministic and does the unglamorous safety work: it checks out the pinned base_sha, excludes the pipeline's own .ai/ scratch from the tree so it doesn't trip the dirty-tree guard, scans for whether the subject ships any tests (test-less subjects get a bigger iteration budget), and — the part worth remembering — if a required vendored script is missing it writes the reason to .ai/setup-error.log and returns invalid before any work starts. The missing-vendor failure is loud and early, not a mysterious mid-run collapse.

Implement — task-runner.dot, the spend-it graph

Merging the capsule PR is the build signal. Implement takes the capsule and writes real code until the gate is green — and then, and only then, submits it to the two-critic consensus. The handoff is quiet by design: the capsule's .md and .verify.sh are same-stem siblings, so passing the .md path satisfies this graph's "find the DoD script" convention on the first try, with no fallback.

05A real capsule, end to end

One off-by-one bug, one gate, two stages

This is a representative defect capsule, is_within_upper_bound_exclusion. The bug — is_within(x, low, high) wrongly excludes the upper bound though the range is meant to be inclusive. Watch how the definition of done becomes a script, gets proven, and then gets spent.

The DEFINITION — a spec with a machine-checkable header

The .md opens with frontmatter the pipeline enforces mechanically, then a fixed four-section body (## Goal, ## Why this matters, ## Definition of done, ## Non-goals):

---
id: is_within_upper_bound_exclusion
title: is_within() wrongly excludes the upper bound though the range is inclusive
red_signal: FAIL: Upper bound excluded   # the exact string the RED run must print
base_sha: 1b60d2a2cb5fca9fe799408da79efc4c23948276
target_repo: https://github.com/example-org/example-repo
verify: DEFINITION.verify.sh
---

## Definition of done
  exit 0: Bug is not present (fixed)
  exit 1: Bug is present (upper bound excluded)
  exit ≥2: Infrastructure problem

The gate — a witness that can't be enumerated away

The verify.sh begins set -euo pipefail and tests random inclusive ranges rather than fixed values, so a "fix" that special-cases the one input in the spec cannot pass. The DEFINITION says so out loud: "the script uses runtime-generated random bounds across multiple test cases to prevent value-specific dodges."

set -euo pipefail
# … three random inclusive ranges …
    low  = random.randint(0, 100)
    high = low + random.randint(1, 100)
    upper_result = is_within(high, low, high)
    if upper_result is not True:
        print(f'FAIL: Upper bound excluded: is_within({high},{low},{high}) '
              f'returned {upper_result}, expected True')
        sys.exit(1)

Stage 1 — specify builds and proves it

  1. setup · preflight

    Checks out base_sha 1b60d2a2…, excludes .ai/ from the tree, confirms the vendored leak-scanner is present. Clean tree, valid input — route to orient.

  2. orient · rival · author

    A brief is drafted; a gate-blind rival writes a steelman fix of the issue before any gate exists; then author writes the capsule pair — the DEFINITION and the random-range verify.sh.

  3. capsule_gate · leak_gate

    Cheap checks first: the pair exists and is non-empty, the script starts set -euo pipefail, the frontmatter carries red_signal/id/title, and no leaked internal vocabulary. Shape OK, vocabulary clean.

  4. redgate · the RED proof

    The gate runs at base_sha. It exits 1 and the log contains FAIL: Upper bound excluded. Both conditions hold, so the red is red for the stated reason. Route to the mutators.

  5. mutate · mutate_b · void → nonvacuity_gate

    Two crude, shape-different patches each drive the gate to 0 — it is reachable and not vacuous. The void probe tries to delete the witness; any greening dodge is archived and re-run against this and every future round.

  6. critique · verdict

    One judge from a second model family reads the vetted draft and ends with an anchored VERDICT: SHIP. The deterministic verdict node accepts only that exact line.

  7. discrimination_check · package

    Here, no later_commit was supplied, so the over-broadness check is skipped with a written reason — recorded honestly in .discrimination.md. package copies the proven capsule out. A human can now approve it in minutes and merge the capsule PR.

Stage 2 — implement spends it

  1. setup · orient · attempt

    The merged capsule's .md path resolves its same-stem .verify.sh on the first try. A maker writes the real fix — making is_within inclusive at the upper bound.

  2. verify · the convergence loop

    The cheap gate runs the capsule's own verify.sh. Red on the first pass routes through triage back to attempt, spending one budget unit per ledger entry; green makes the run eligible, not done.

  3. critique A · stamp_a · critique B

    Reviewer A judges and writes its verdict; stamp_a snapshots its sha256; reviewer B — a different model family, forbidden from reading A's file — judges independently.

  4. verdict · package · ship_check

    Both said SHIP, so the deterministic gate passes. package commits to a task/<id> branch; ship_check asserts the .ai/ scratch is gone and the tree is clean. The preserved plumbing opens the fix PR.

What the two stages guarantee together

Specify guarantees the gate is a good judge — red for the right reason, reachable, not (where checked) over-broad, vocabulary-clean, blessed by an independent critic. Implement guarantees the fix passes that gate and survives two independent critics who must agree. Neither stage lets an LLM's opinion of its own work end the run.

06What it is — and is not

A gate is only worth as much as its proofs

The capsule is a specific answer to a specific problem: turning an unenforceable "done" into an executable, adversarially-vetted one. Being honest about its edges is part of the design, not a disclaimer bolted on.

What a capsule is

A falsifiable definition of done: a script whose exit code decides the question, shipped with the evidence that it goes red on the real bug, can be greened, and was judged by an independent critic.

A read-only proposal a human approves on the strength of those proofs — then a build loop that must satisfy the gate and a two-family consensus before it commits.

What a capsule is not

Not a guarantee the fix is correct — it is a guarantee the fix passes a gate that was itself vetted. A weak or skipped proof (a skipped discrimination check) is a weaker guarantee, and the capsule says so on its face.

Not a wiring guide. The GitHub-Actions plumbing that triggers it is deliberately out of scope here; the interesting thing is the artifact and its proofs, not the CI that fires them.

Where to be careful

  1. Did the discrimination check actually run?

    If .discrimination.md records a skip, the gate was never proven to be non-over-broad. It may still be a fine gate — but that specific assurance is absent, by the capsule's own admission.

  2. Were both critics really independent?

    Consensus is only meaningful if the second family was actually present and blind to the first. A silently-degraded critic turns "two agreed" into "one spoke twice."

  3. Is the shipped script the proven script?

    The proofs are about bytes. If anything rewrites the gate between proving and shipping, the proofs no longer describe what arrives — which is exactly why the shipped bytes are re-verified from a clean tree.

"Nothing with a measured miss record gets acquittal power over an executed result."
